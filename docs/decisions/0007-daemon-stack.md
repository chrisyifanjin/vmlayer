# 0007. Daemon stack: tonic gRPC over a unix socket, SQLite, bollard

Status: accepted, 2026-11-14

## Context

ADR 0002 fixed the shape: one `vmlayerd` per host, thin SDKs. This record
fixes the concrete stack so the daemon, the first backend and the Python
client can be written without revisiting it.

## Decisions

**Wire protocol: gRPC, protobuf, `vmlayer.v1` package.** Rust side `tonic`
0.14 + `prost` 0.14; Python side `grpcio` with generated stubs checked in
(regenerated by `make proto`, verified unchanged in CI). gRPC gives
streaming (process output, pty, file transfer) and typed errors for free and
has first-class clients in every SDK language we plan. REST is not offered;
an E2B-compatible HTTP facade (docs/e2b-mapping.md) is a separate adapter.
The proto file is the contract; `core` types mirror it and conversion lives
in one module (`daemon/src/convert.rs`).

**Transport: unix socket by default, TCP opt-in.** `$XDG_RUNTIME_DIR/vmlayer/vmlayerd.sock`
(Linux) or `~/.vmlayer/vmlayerd.sock` (macOS), file mode 0660. TCP listener
only with `--listen tcp://host:port` and a bearer token; the daemon refuses
TCP without a token. This is what Docker does and what every SDK user
expects.

**State: SQLite via `rusqlite` (bundled), WAL mode, one file in the data dir.**
Tables: sandboxes, volumes, volume_snapshots, snapshots, mounts, processes.
Access through one `Store` type with blocking calls run on
`spawn_blocking`; no ORM. Migrations are numbered SQL files embedded in the
binary. Postgres is not supported in v1: the daemon is per-host and its
state is per-host (ADR 0005).

**Docker backend: `bollard`.** Pure-Rust Docker Engine API client, async,
maintained; it covers exec with tty, attach streams, archive upload and
download, pause and unpause, which is everything `SandboxHandle` needs.
Port exposure after start is done by a helper container joined to the
sandbox's network namespace (`--network container:<id>`) publishing the
port, since Docker cannot add port mappings to a running container.

**Process model: the backend owns processes, the daemon owns ids.** For the
Docker backend a `Process` wraps a Docker exec instance. Output not yet read
by any client is buffered in the daemon up to a per-process cap (default
8 MiB, then oldest dropped and flagged) so `process(pid)` after a reconnect
sees recent output. The guest-agent-based backends buffer in the guest
instead.

**Observability: `tracing` with JSON or pretty output, a `/healthz`-equivalent
`System.Health` RPC, and per-RPC spans carrying sandbox id.** Metrics
(Prometheus) come with the cluster layer, not v1.

**Config: one TOML file plus flags via `clap`; flags override file.** Defaults
work with no file at all. Data dir defaults to `/var/lib/vmlayer` when root,
`~/.vmlayer` otherwise.

**Image resolution for Docker: pass-through.** The Docker backend accepts
`Rootfs::EngineImage` and lets dockerd pull. The OCI→ext4/EROFS pipeline
(for Firecracker and libkrun) is step 4 work and will produce the other
`Rootfs` variants; the Docker backend ignores them with `Unsupported`.

## Layout

```
proto/            vmlayer/v1/*.proto, Rust crate vmlayer-proto (tonic-build)
daemon/           vmlayerd binary: server, store, volume store, backend registry
backends/docker/  vmlayer-backend-docker
backends/firecracker/  vmlayer-backend-firecracker (Linux only)
guest-agent/      static Linux binary, vsock server
sdk/python/       generated stubs under vmlayer/_proto/, client in vmlayer/_client/
cli/              `vmlayer` command: thin wrapper over the gRPC API for humans
```

## Consequences

- `protoc` is a build dependency for the Rust proto crate and for stub
  regeneration; CI installs it. Users of the Python SDK never need it.
- Every SDK method maps to exactly one RPC; the SDK does not combine RPCs
  into transactions. Anything that must be atomic (snapshot with volumes)
  is one RPC.
